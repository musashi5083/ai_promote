道 1 ／ gbrain 本体をそのまま動かす

gbrain 起動ランブック

原理を移植する前に、本物を動かして何が効くのかを体感するための手順。最重要の検証（日本語で検索品質が出るか）は Phase 1 で終わり、そこまで Neon も Railway も要らない。クラウドに手を出すのは、ローカルで手応えが出てからでいい。

前提 Cloudflare / Neon / Railway / Resend ＋ 追加で API キー 2 本 Phase 0–1 ローカルのみ・45 分 Phase 2–3 クラウド・2〜3 時間
事前

用意するもの

4 サービスのうち、Phase 0–1 ではひとつも使わない。必要なのは Bun とキー 2 本だけ。

訂正

前回「Cloudflare Workers AI の bge-m3 で埋め込みを賄える」と書いたが、gbrain のネイティブ埋め込みプロバイダに Cloudflare は入っていない（Voyage / OpenAI / OpenRouter / Gemini / Azure OpenAI / MiniMax / DashScope / Zhipu / Ollama / llama-server / LiteLLM）。OPENAI_BASE_URL で OpenAI 互換ゲートウェイに向けられるので CF の互換エンドポイント経由で通る可能性はあるが、初回に賭ける場所ではない。

bge-m3 が活きるのは、原理だけ自作する道 2 のほう。道 1 では Voyage で始める。

入れる中身の線引き

個人環境で試す以上、投入するのは私用のメモか、業務を模したダミーに限ること。社内のメールや文書を個人の Neon / Railway に置いた時点で、検証の是非以前に規程の問題になる。ここで測りたいのは仕組みの挙動であって、実データが載るかどうかではない。日本語で 50〜200 ページあれば品質は十分に測れる。

Phase 0

ローカルで動かす

15 分・キーもクラウドも不要

gbrain はキーゼロでも起動する（キーワード検索と、エージェントが自分で書いたメモリだけが動く）。まずここまでを最短で通して、壊れていないことを確認する。

0-1インストール

curl -fsSL https://bun.sh/install | bash
bun install -g github:garrytan/gbrain#latest-stable
最初の罠

npm install -g gbrain は絶対に実行しない。npm 上の gbrain はこのプロジェクトとは無関係の別パッケージで、PATH 上で本物を覆い隠す。入れてしまったら npm uninstall -g gbrain してから GitHub 経由で入れ直す（gbrain doctor はこの状態を検出して直し方を出す）。

bun install -g が postinstall で失敗する環境では、確実な代替がある：git clone https://github.com/garrytan/gbrain.git ~/gbrain && cd ~/gbrain && bun install && bun link

0-2脳を作る

gbrain init --pglite   # 2 秒。サーバも Docker も要らない
gbrain doctor          # 全チェックが ok になること

--pglite は Postgres 17 を WASM で埋め込んだ組み込みエンジン。本物の Postgres と同じ SQL・同じ全文検索の制約を持つので、Phase 1 の日本語検証はここで正しく測れる。

0-3往復を確かめる

gbrain capture "個人検証を Phase 0 から始めることにした。理由は日本語の検索品質がローカルで測り切れるから。"
gbrain search "日本語 検索"
gbrain stats
Checkpoint 0

gbrain doctor が全項目 ok、gbrain search がいま書いたページを返す。ここまで 15 分。通らなければ先に進まない——Neon も Railway も、この土台の上にしか乗らない。

Phase 1

日本語で品質を測る — ここが本題

30 分・まだローカルのみ

設計ノート 05 で残した「日本語で検索品質が本当に出るか」を、ここで潰す。PGLite は本物の Postgres なので、Neon に載せても答えは変わらない。クラウドに一銭も払う前に結論が出る。

1-1キーを入れる

export VOYAGE_API_KEY=pa-...
export ANTHROPIC_API_KEY=sk-ant-...
キーの置き場所を間違えない

gbrain config set で API キーを設定してはいけない。そちらは DB 側の設定面に書き込まれ、埋め込みパイプラインは読まない。キーは環境変数か ~/.gbrain/config.json（ファイル面）に置く。ドキュメントが明示的に警告している罠で、静かに失敗するので気づきにくい。

常駐デーモンに移すときはさらに別で、~/.gbrain/env（0600、gbrain autopilot --install が作る）に置く。対話シェルの rc ファイルはデーモンのシェルには届かない。

1-2日本語の素材を入れて全部立てる

gbrain import ~/notes          # 私用の md を 50〜200 枚
gbrain embed --all             # ベクトル
gbrain extract all             # ★ グラフ。これが +31 P@5 の正体
gbrain stats

extract all を飛ばさないこと。リンクとタイムラインからグラフを張る工程で、LLM を一切呼ばないのに検索品質を最も大きく動かす。

1-3質問 20 本で数える

自分が実際に投げたい日本語の質問を 20 本用意して、3 つの入口を比べる。

gbrain search "..."            # 生の検索（ハイブリッド、LLM コストなし）
gbrain query  "..."            # 拡張つきのフル制御版
gbrain think  "..."            # 引用つきの合成回答 ＋ 不足の明示

外した質問は、当てずっぽうで直さずに理由を出させる。

gbrain search "..." --explain                    # どの層が効いたか／各ブーストの寄与
gbrain search diagnose "..." --target <slug>     # なぜそのページが出なかったか

1-4何が起きるはずか（先に仮説を置く）

PostgreSQL の全文検索は日本語を語に割れない。GBRAIN_FTS_LANGUAGE は既定で english だが、これを何に変えても日本語用の構成は Postgres 側に存在しない。つまりハイブリッド検索の BM25 アームは、日本語ではほぼ機能しないはず。

したがって測りたいのは「全体として何点か」ではなく、こちらの問いになる：

キーワード側が死んだ状態で、ベクトル ＋ グラフ ＋ リランカ ＋ タイトル/別名ブーストだけで実用に足りるか。

足りるなら、社内でも PostgreSQL 系で通せる目が出る（AI Search 一択ではなくなる）。足りないなら、設計ノート 06 の 2-gram 方式を自作するか、素直に AI Search の日本語アナライザに頼る——どちらを選ぶかが、ここの実測で決まる。

Checkpoint 1 — このランブックで一番重要

20 本のうち何本が上位 5 件に正解を含んだか、数字で書き留める。--explain の出力から、キーワードアームが実際に何回貢献したかも控える。この 2 つの数字が、社内設計で AI Search に倒した判断を検証する材料になる。

Phase 2

Neon に載せ替える

30 分・ここで原理 1 を実体験する

Neon でプロジェクトを作り、プーラー経由ではない直結の接続文字列を取る（マイグレーションと DDL が通る必要がある）。

2-1移行コマンドを使わず、作り直す

gbrain migrate --to supabase という移行コマンドは存在するが、あえて使わない。脳リポジトリが正で DB は捨てられるキャッシュ、という原理 1 が本当かどうかを、最初の移行で自分の手で確かめる価値がある。

export GBRAIN_HOME=~/.gbrain-neon      # 既存の PGLite 脳は残したまま別の脳を作る
gbrain init --url "postgresql://...neon.tech/neondb?sslmode=require"
gbrain doctor
gbrain import ~/notes
gbrain embed --all
gbrain extract all
gbrain stats                           # Phase 1 と件数が一致すること

Markdown から丸ごと再構築できて、件数も検索結果も一致する——これが確認できたら、原理 1 は自分の環境で証明されたことになる。以後「DB のバックアップ」という発想を捨てられる。

ここで詰まるなら

gbrain の v35 マイグレーションは CREATE EVENT TRIGGER（Neon は neon_superuser 経由で対応済み）に加えて BYPASSRLS も要求する。gbrain doctor がここで落ちたら、Railway の Postgres に切り替える——自前コンテナなので superuser がある。判定は 2 分、粘る価値はない。

そもそもこの自動 RLS は、Supabase が anon キーで public スキーマを公開してしまう事情への対策。Neon にも Railway にもその露出はないので、機能として失うものはない。

Checkpoint 2

gbrain doctor が Neon（または Railway Postgres）で全部 ok。gbrain stats の件数が Phase 1 と一致。Phase 1 の質問 20 本を投げ直して、同じ答えが返る。

Phase 3

Railway で夜間サイクルを回す

1〜2 時間・複利がここから始まる

ここまでは「聞けば答える」道具でしかない。Dream Cycle が回って初めて、翌朝の脳が前日より賢くなる。設計ノート 01 の下側のループがこれ。

3-1まずローカルで 1 周させる

gbrain dream --dry-run --json    # 何が起きるか
gbrain dream --json              # 本番 1 周

出力の details.synthesis を読む。安いモデルの triage スコアで足切りされた件数と、実際に合成されたページ数が出る。ここでコスト感を掴んでから常駐させる。

3-2Railway に置く

リポジトリに Dockerfile は同梱されていないので、Bun のビルドパックか自前 Dockerfile で。環境変数はローカルと同じ 3 つ（GBRAIN_DATABASE_URL / VOYAGE_API_KEY / ANTHROPIC_API_KEY）に GBRAIN_HOME を加える。

  • cron：毎晩 gbrain dream。これが本体。
  • 常駐ワーカー：重い処理を投げるようになったら gbrain jobs supervisor。リポジトリの docs/guides/minions-deployment-snippets/Procfile がそのまま使える（Render / Railway / Heroku 共通）。
  • 脳リポジトリの同期：起動時に private リポジトリを clone して gbrain sync。書き戻しは gbrain sources push。
Checkpoint 3

翌朝、gbrain dream --json のログに synthesize されたページが残っている。そのページを gbrain think で引けて、引用元が辿れる。ここが Stage 0 の合格ライン——設計ノート 05 の「夜間サイクルが無人で回るか」が、条件付きアクセスの部分を除いて潰れる。

次回

Cloudflare と Resend

取り込み口（Resend Inbound → Cloudflare Worker → /ingest）と朝のブリーフィング配信は Phase 4 として分ける。Phase 3 まで動いてからでいい——取り込みを自動化しても、脳が答えを返さなければ意味がないので。

途中で全体の設計に戻りたくなったら、設計ノートの 05（残る検証項目）と 06（個人環境の割り当て）が対になっている。

コマンドと制約は gbrain リポジトリの README.md / docs/INSTALL.md / docs/ENGINES.md / docs/integrations/embedding-providers.md / docs/guides/minions-deployment.md を実際に読んで確認したもの。gbrain は活発に更新されているため、詰まったらまず gbrain doctor、次に gbrain bootstrap verify（インストール契約を丸ごと検証して非ゼロ終了する）を走らせること。
