GBrain を規制下の社内で
再現するための設計

Garry Tan の GBrain（MIT・公開リポジトリ）を実際に読み、「何が効いているのか」を原理まで分解したうえで、Microsoft 365 / Azure の統制下でどこまで同じものが成立するかを詰めた。結論から言うと、価値の大半はインフラではなく運用規律にあり、その部分は承認を待たずに今日から始められる。

01

GBrain の正体 — 検索エンジンではなく、夜通し働く常駐プロセス

GBrain は「Markdown のメモを Postgres に索引する道具」として説明されがちだが、それは一番外側の皮でしかない。実際に効いているのは次の 7 つで、順番に重要度が高い。ここを取り違えると、DB を立てただけで何も compound しないものが出来上がる。

原理 1正はリポジトリ、DB は捨てられるキャッシュ

Markdown ＋ frontmatter を置いた Git リポジトリが system of record であり、Postgres は派生インデックスに過ぎない。DB のバックアップを取らないのが設計上の宣言で、壊れたら sync と extract で全部作り直す。CI がこの不変条件を機械的に検査していて、派生テーブルへ直接書く新規コードは落とされる。

この一手で、災害復旧・複数マシン同期（＝ git pull）・ベンダーロックイン回避・監査可能性がまとめて片付く。社内提案の文脈ではこう言い換えられる。「AI が作った知識資産が、最終的にどこに何の形で残るのか」を情シスに一文で説明できる唯一の構成である。

原理 2Thin harness, Fat skills — Markdown が実行可能な手続きになる

スキルは Markdown ファイルで、引数を取るメソッド呼び出しとして振る舞う。同じ /investigate が、渡す対象を変えるだけで医療研究アナリストにも不正調査官にもなる。LLM を回すハーネス側は薄く保ち、ツール定義でコンテキストを食い潰さない。

規制環境で効いてくるのは説明責任のほうだ。「なぜエージェントがそう動いたか」がスタックトレースでも設定スキーマでもなく、人間が読める Markdown 1 枚に書いてある。監査でそのまま出せる。Garry 自身の CLAUDE.md が 2 万行に膨れて破綻し、200 行のポインタ集に戻したという告白も、そのまま社内ドキュメントの教訓になる。

一度きりの仕事はするな。また必要になる類のことなら、まず 3〜10 件手でやって出力を見せろ。承認されたらスキルファイルに固定しろ。自動で回すべきなら cron に載せろ。同じことを二度頼まれたら、その時点で失敗だ。 Garry Tan — 自分の常駐エージェントに与えた運用規律

原理 3Latent（判断）と Deterministic（信頼）を混ぜない

読解・統合・パターン認識は LLM 側、数える・並べる・割り当てる・SQL はコード側。「8 人の席順は LLM に組ませられる。800 人を頼むと、もっともらしい嘘の座席表が出てくる」。決定論的な問題を latent 側に押し込んだ瞬間にシステムは壊れる。

社内的な意味は明確で、監査・再現性の対象になるのは deterministic 側だけになる。ここを固く作れば審査は通しやすくなるし、逆にここを LLM に任せると「毎回答えが違う業務システム」として突き返される。

原理 4LLM を一切呼ばない自己配線グラフ（費用対効果が最大）

ページを書き込むたびに正規表現 3 本で [[wiki/people/bob]] 形式と Markdown リンクを拾い、型付きエッジ（works_at / attended / invested_in …）を SQL 一発で一括 INSERT する。LLM コールもトークンも 0。1.7 万ページで全グラフ抽出が数秒。

効果は誇張ではない。240 ページのベンチマークで、グラフ無効時 P@5 が約 18 だったものが 49.1（+31 ポイント）まで跳ねる。ripgrep/BM25 のみ、ベクトルのみの標準 RAG も同じく約 18 で並ぶ。つまりグラフは「あると良い機能」ではなく耐力壁であり、しかもコストがゼロに近い。社内移植で最初に入れるべきはここ。

原理 5ハイブリッド検索と、スコアではなく「根拠」を返す契約

ベクトル（HNSW）＋ BM25 ＋ RRF 融合 ＋ ソース重み ＋ 意図分類 ＋ クロスエンコーダのリランク ＋ 別名解決を積み上げている。リランカだけで上位 1 位の 6 割が入れ替わる。

設計として見習う価値があるのは順位そのものより返り値のほうで、各結果に evidence（なぜ当たったか：別名一致／完全タイトル一致／高ベクトル一致／キーワード一致／弱い意味的一致）と create_safety（そのページはもう存在するか）が付く。エージェントが生スコアの数字で博打を打たなくて済む。これは自作する側にとっても真似しやすい契約だ。

原理 6ページの二層構造 — Compiled Truth と Timeline

すべてのページが上下 2 ゾーンに分かれる。上は compiled truth（現時点の要約。証拠が増えるたび書き換える）、下は timeline（追記のみ・編集禁止・日付と出典つきの証拠列）。「人物を理解するのに 200 件のログを読ませない。30 秒で状況が分かる 1 段落と、その裏付け」という発想である。

さらに知識を 2 層に分ける。Facts（熱い記憶＝本人が会話で言ったこと）と Takes（冷たい記憶＝誰が何を、どれくらいの確信度で信じているか。take／fact／bet／hunch）。両者は絶対に混ぜず、夜間サイクルの consolidate フェーズだけが一方向に昇格させる。

ここが RAG との決定的な差になる。RAG はチャンクを返す。ブレインは読んで書いた結果を返す。

原理 7Dream Cycle — 複利を回している本体

毎晩走る保守サイクル（lint → バックリンク修復 → extract → sync → embed → synthesize → consolidate）が、実質的に GBrain の本体である。コスト制御も作り込まれていて、安いモデルで各素材に triage スコアを付けてキャッシュし、閾値でゲートする。閾値を変えても再判定は LLM 0 コールで済む。

チャット上でエージェントに頑張らせ続けるより、24 時間動いて取り込み・エンリッチ・統合をやるデーモンを出荷するほうが簡単だ。 GBrain README — 設計思想の核心

ここまでの結論。GBrain の価値の 8 割は、DB でもモデルでもなく 原理 1・2・3・7 という運用規律にある。これは規制環境でも 100% 再現できるし、Azure の承認を待つ必要もない。手間がかかるのはインフラの一部だけだ。

02

層ごとの写像 — Microsoft 環境に何を割り当てるか

層に分けて見ると、検索とインフラの層は Azure 側にほぼ既製品があり、むしろ楽になる部分すらある。難所は 2 つに集中する。エージェントをどこで動かすかと、アクセス権をどう継承させるかだ。

Azure サブスクリプションと Azure OpenAI が使える前提が立ち、初期スコープが自分 1 人と決まったので、候補はほぼ一本に絞れる。下表の太字が採用案。ひとつだけ、当初 PostgreSQL ＋ pgvector を推していた索引層は結論が変わった——日本語という条件を入れると答えが逆転する（次の見出しで説明する）。

索引層だけは、日本語という条件で結論が逆転する

純粋に GBrain の原理を写すだけなら PostgreSQL ＋ pgvector が有利だ。エッジをテーブルに持てば JOIN でグラフを歩けるし、RRF も SQL で書ける。コストも桁違いに安い。実際、脳の中身が英語ならこちらを勧める。

ところが脳の中身が日本語主体になると前提が崩れる。PostgreSQL の全文検索は日本語を分かち書きできない——標準では日本語用の text search configuration が存在しない。GBrain 自身も GBRAIN_FTS_LANGUAGE で言語を切り替えられるようにしているが、選べるのは Postgres が持っている構成だけで、日本語はその中にない。つまりハイブリッド検索の BM25 アームが丸ごと死ぬ。原理 5 の「ベクトルが意味の隣に流れたときにキーワードが拾い直す」という補完関係が成立しなくなる。

回避策はある（pg_bigm による 2-gram、pg_trgm による 3-gram）が、前者はマネージド環境での可用性を確認する必要があり、後者は日本語では精度が落ちる。一方 Azure AI Search は日本語アナライザを標準で持ち、セマンティックランカーも日本語に対応している。ここで天秤が傾く。

失うのは JOIN による多段グラフ探索だが、これは代替できる。GBrain 自身の検索パイプラインでもグラフ拡張は2 パス方式（1 回目のヒット集合の隣接ページを 2 回目で引く）として実装されていて、深い再帰探索ではない。各ドキュメントに linked_slugs 配列を持たせておけば、AI Search でも同じことが 2 クエリでできる。耐力壁は落とさずに済む。

注：Azure / Graph 側の各サービスの可用性・権限名・リージョン制約・拡張機能のサポート状況は変わるため、稟議に出す前に最新の公式ドキュメントで裏を取ること。ここでは構成の当たりを付けるところまで。

03

そのままでは効かない — 規制環境固有の 6 つの落とし穴

ここが一番重要なパート。GBrain は「一人の人間の脳」として設計されていて、その前提が社内では成り立たない。技術的に動くものを作った後で気づくと、全部作り直しになる種類の問題を先に並べる。

最重要アクセス権が派生物に継承されない

SharePoint の限定サイトや個人メールから取り込んだ内容が、Markdown ページになった瞬間に元の権限を失う。「A さんの人事メールから作られた人物ページが、B さんの検索でヒットする」が普通に起きる。これは Copilot 導入時に各社が踏んだ oversharing 問題と同じ構造で、後から権限を付け直すことは原理的にできない（どの文の出所がどれか、もう分からなくなっている）。

設計原則権限は取り込みの瞬間に確定させ、検索時に必ず適用する。全ページに acl（Entra グループ OID の配列）を必須フィールドにし、複数ソースから合成したページの権限は積集合＝最も狭い方を採る。取り込み経路は委任権限（本人が見えるものだけ）から始め、アプリケーション権限（テナント全体）は Stage 2 まで使わない。

法務人物ページは従業員プロファイリングになる

GBrain の person ページのテンプレートには ## Assessment という欄が実在し、公式ドキュメントの例文はこうだ ——「鋭い技術リーダー。社内では過小評価されている。燃え尽きの兆候に注意」。投資先の創業者に対してなら有効な機能だが、社内の同僚に対して同じものを自動生成した瞬間に、労務・個人情報の問題に変わる。人事評価への転用、本人非開示、利用目的外利用のどれもが論点になる。

設計原則社内の人物ページは「業務上の事実 ＋ 出典」だけに絞る（役割・担当・直近のやりとり・未クローズの依頼）。評価・推測・性格・健康・将来予測の欄はスキーマから物理的に削る——「書かない運用にする」では必ず漏れる。そのうえで人事・法務レビューを Stage 1 の着手前に通す。ここを飛ばすと、動いてから全部止まる。

Purview秘密度ラベルと DLP が派生物に付かない

ラベル付き文書を Markdown に落とした時点でラベルは消え、埋め込みベクトルにも当然付かない。しかも「ベクトルなら中身は分からないから安全」は成り立たない——埋め込みからの原文復元は現実的な攻撃として知られている。索引そのものを保護対象として扱う必要がある。

設計原則ラベルを frontmatter に持ち上げて派生物に運ぶ。ラベルごとにインデックスとストレージを分ける（社外秘以上は別コンテナ・別キー・別接続）。ラベル未判定の素材は取り込まない（fail-closed）。

削除「忘却」の設計と削除請求が正面から矛盾する

GBrain の forget は削除ではない。該当行に取り消し線を引き、valid_until と理由を刻んで監査履歴として残す設計になっている。個人データの削除請求・退職者データ・誤取り込みへの対応としては、これは使えない。逆に、保持ポリシーや eDiscovery ホールドがかかった領域から取り込んだページは勝手に消せない、という反対方向の制約も同時に効いてくる。

設計原則論理的な「忘却」とは別に、ハードデリート経路を最初から設計に含める。Git 履歴からの除去（履歴書き換え）、索引からの削除、埋め込みの再構築までを 1 つの手順書にする。同時に、取り込み元ごとに「消せる／消せない」を frontmatter に持たせて区別する。

実行環境エージェントを動かす場所がない

統制端末では任意の OSS・npm・ランタイムを入れられず、外向き通信も塞がっているのが普通。GBrain の想定する「手元の CLI ＋ ローカル DB」は成立しない。

設計原則ハーネスはサーバ側（Azure）に置き、利用者は Teams ボットか社内 Web から話す。端末には何も入れない。これは GBrain 自身の Topology 2（thin client：エージェントの機械にはローカル DB を持たず、すべて host 側で処理）そのもので、移植先の制約に元設計が既に対応している数少ない領域。

調達本体の持ち込み審査より、原理の移植のほうが速い

gbrain 本体は TypeScript ＋ Bun、ソース 3,000 ファイル規模、依存も多い。SBOM・脆弱性・ライセンス・サプライチェーンの審査コストは相当に高く、しかも通ったところで Microsoft 環境向けの取り込み経路と権限モデルは自分で書くことになる。

設計原則まず読んで原理を移植する。特に効き目の大きい 原理 4（自己配線グラフ）は正規表現数本と SQL 1 本、原理 6（二層ページ）はスキーマの取り決めに過ぎない。動くものが出来て価値が実証できてから、必要なら本体導入を審査に回す——順序が逆だと、審査待ちのまま何も学べない期間が数か月続く。
04

段階設計 — 承認を待たずに始められるところから

Azure が使える見込みが立った今でも、Stage 0 を今週始めることを勧める。理由は 01 の結論そのままで、価値の 8 割が運用規律にあり、そこは Azure OpenAI の申請結果を待たずに始められるから。そして Stage 0 の成果物（Markdown の脳とスキルファイル群）は、最終的にどの技術構成を選んでも 100% そのまま使える。それが「正はリポジトリ」という設計の本当の意味だ。申請と Stage 0 は並走させる。

Stage 0
一人ぶんの脳 2〜4 週間・承認不要・並走で申請
  • 置き場：Azure DevOps に個人リポジトリを 1 本。Markdown だけ。DB もベクトルも要らない。
  • スキーマは 6 型で始める：person / company / meeting / concept / decision / note。GBrain の 15 型は 15 万ページ規模で必要になったもので、最初から真似する必要はない。
  • ページ構造だけは最初から守る：上に compiled truth、<!-- timeline --> より下に日付＋出典の追記のみ。ここが後から直すのが一番つらい部分。
  • frontmatter に acl と label を最初から必須にする。今は誰も読まないが、Stage 2 で付け直すことは原理的にできない（03 の 1・3 番目）。
  • 人物ページは業務事実のみ（03 の 2 番目）。この時点で評価欄を作らないと、癖として残る。
  • 検索は既存の grep で十分。先に「書く規律」を作る。
  • 二度やった作業は Markdown のスキルに固定する。会議メモの整形、週次まとめ、人物ページの更新手順——この資産が Stage 1 以降の中身になる。

並走させること：Azure OpenAI の申請、そして情シスへの 2 つの確認（条件付きアクセス下でバックグラウンドの Graph 更新が通るか／Teams トランスクリプトの扱い）。どちらも Stage 1 の律速になる。

Stage 1
自分の脳を自動で回す 1〜2 か月・自分 1 人のまま

ここはまだチームに広げない。自分 1 人のまま、取り込みと夜間サイクルを自動化するのが Stage 1 の目的。委任権限で自分に見えるものしか入らないので、03 の 1 番目（権限継承）が構造的に回避される——この安全地帯にいる間に、原理 4・6・7 を動かして価値を実証する。

  • Azure AI Search に索引を作る（日本語アナライザ ＋ ベクトル ＋ セマンティックランカー）。埋め込みと生成は Azure OpenAI。
  • 自己配線グラフを実装（原理 4）。リンク抽出 ＋ linked_slugs ＋ 2 パス拡張。ここで検索品質が跳ねる。LLM コストはかからないので、最初に作る。
  • Graph delta で取り込み。予定表 → メール → OneDrive/SharePoint 文書 の順（実装が軽く効果が大きい順）。Teams トランスクリプトは 05 の経路で別途。
  • 認証は Key Vault の refresh token 方式。ここが最初に詰まるので、Stage 0 のうちに情シス確認を済ませておく。
  • 夜間 Dream Cycle を Container Apps Jobs で。ここを飛ばすと Stage 0 の延長にしかならない。安いモデルの triage スコアでゲートするコスト制御も最初から入れる。
  • 問い合わせ口は自分専用の Teams ボット。端末には何も入れない。
判定朝いちばんに脳のほうから何か出てくるか（前夜の統合結果、今日の予定に紐づく文脈）。「聞けば答える」で止まっているなら、まだ Dream Cycle が効いていない。
Stage 2
チームへ広げる Stage 1 の実績が出てから

ここで初めて権限設計が主題になる。他人が自分の検索結果を見る瞬間に、Stage 1 の安全地帯は終わる。技術より先に、人事・法務レビュー（03 の 2 番目）を通すのがこの段階のゲート。

  • Entra アプリロール ＋ On-Behalf-Of で、利用者ごとの可視範囲を認可基盤側に寄せる。
  • AI Search のセキュリティフィルタを必須に。フィルタなしで検索を呼べる経路をコード上に残さない。
  • 秘密度ラベル別のインデックス分離（03 の 3 番目）。Stage 0 から label を刻んでいれば、ここは分けるだけで済む。
  • ソース分割（共有 wiki／顧客／社内限定）と越境読みの拒否をデータ層で強制。
  • ハードデリート運用手順の整備と、実際に消せることの訓練（03 の 4 番目）。Purview 監査ログ連携もここ。
05

決まったこと、まだ潰れていない 3 つ

前提が 4 つとも固まったので、構成の分岐はほぼ閉じた。Azure サブスクリプションあり／Azure OpenAI 申請可／初期スコープは自分 1 人／取り込みは予定表・メール・Teams トランスクリプト・OneDrive 文書の 4 系統。残るのは、動かしてみないと分からない 3 点だけ。どれも Stage 0 と並走で潰せる。

Teams トランスクリプトだけ、経路が違う

Graph の会議トランスクリプト API はアプリケーション権限が前提で、テナント管理者の同意とアクセスポリシー設定が要る。委任権限では取れないため、「自分 1 人で始める」が唯一できない取り込み源になる。現実的な第一歩は、会議の録画・文字起こしが OneDrive／SharePoint に残る性質を使って Files.Read（委任）で .vtt を拾う経路。テナント設定次第なので、まず 1 件手で辿って確かめる。

→ 4 系統のうち 3 系統は自力で進む。ここだけ情シス案件

夜間ジョブが自分の権限で Graph を叩けるか

委任権限のバックグラウンド実行は refresh token の維持で成立するが、条件付きアクセス（MFA 頻度、準拠デバイス要求、セッション制御）がかかっていると更新が弾かれることがある。Stage 1 で最初に詰まる確率が一番高い場所。Stage 0 のうちに、小さなスクリプトで「翌日も無人でトークンが更新できるか」だけ実測しておく。

→ ここが通らないと Dream Cycle が無人で回らない

日本語で検索品質が本当に出るか

AI Search の日本語アナライザとセマンティックランカーを選んだのは机上の理由なので、実測で裏を取る。Stage 0 で溜まった数百ページを索引に入れ、自分が実際に投げたい質問を 20 本用意して P@5 を手で数えるだけでいい。GBrain 自身がグラフなしで約 18、ありで 49.1 という数字を出しているので、比較の目盛りは既にある。

→ 索引層の選択を早期に検証できる。外れても Stage 1 の中で差し替えられる

この 3 つに共通する性質

いずれも調べても答えが出ず、小さく試せば 1 日で分かる類のもの。稟議や設計会議で潰そうとすると数週間かかるが、Stage 0 の片手間で実測すれば片付く。設計をこれ以上机上で進める価値は低い——次の一手は、書き始めることと、この 3 つの実測。

→ 設計フェーズはここで終わってよい
